## 1. Общие положения

### 1.1. Назначение системы

Telegram-бот для приема обращений пользователей и интеграции с системой управления заявками Assyst. Бот обеспечивает двустороннюю синхронизацию: создание заявок из Telegram в Assyst и получение уведомлений об изменении статусов заявок.

### 1.2. Цели

- **Снижение нагрузки** на специалистов технической поддержки
- **Сокращение времени регистрации** обращения до 2 минут
- **Автоматизация процесса** создания и обработки заявок
- **Информирование пользователей** о статусе их обращений в режиме реального времени

### 1.3. Используемые системы

- **Telegram** — платформа для взаимодействия с пользователями
- **Apex** — система для проверки пользователей и их проектов
- **Assyst** — система управления заявками (Service Desk)
- **БД бота** — локальная база данных для хранения информации о заявках и пользователях

## 2. Архитектура системы

### 2.1. Компоненты системы

```
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│   Telegram   │◄───────►│  Telegram    │◄───────►│    Apex      │
│     User     │         │     Bot      │         │   (проверка) │
└──────────────┘         └──────┬───────┘         └──────────────┘
                                │
                                │
                   ┌────────────┼────────────┐
                   │                         │
                   ▼                         ▼
         ┌──────────────────┐    ┌──────────────────┐
         │   БД бота        │    │     Assyst       │
         │ (заявки, users)  │    │  (Service Desk)  │
         └──────────────────┘    └──────────────────┘
```

### 2.2. Поток данных

**Создание заявки:**
1. Пользователь → Telegram Bot (авторизация, ввод данных)
2. Telegram Bot → Apex (проверка пользователя, получение проектов)
3. Telegram Bot → Assyst (создание заявки через email на `assyst.inbox@onlanta.ru`)
4. Assyst → Telegram Bot (webhook о регистрации заявки)
5. Telegram Bot → БД бота (сохранение информации)
6. Telegram Bot → Пользователь (уведомление о создании)

**Изменение статуса:**
1. Специалист → Assyst (изменение статуса)
2. Assyst → Telegram Bot (webhook о изменении)
3. Telegram Bot → БД бота (обновление информации)
4. Telegram Bot → Пользователь (уведомление)

## 3. Модуль авторизации

### 3.1. Согласие на обработку персональных данных

#### Сценарий: Первый запуск бота

При первом запуске `/start` пользователю отображается запрос согласия на обработку персональных данных.

**Сообщение:**

```
Для использования бота необходимо согласие на обработку персональных данных.

Полный текст согласия: https://onlanta.ru/privacy-policy

Нажимая кнопку "Да", вы подтверждаете, что ознакомились и согласны с условиями обработки персональных данных.
```

**Кнопки:**
- `✅ Да` — пользователь дает согласие и продолжает работу с ботом

**Примечание:** Текст согласия предоставляет СИБ, его необходимо разместить на сайте onlanta.ru.

---

### 3.2. Авторизация по email

#### Сценарий 1: Старт после согласия

1. **Пользователь** нажимает `✅ Да` (или вводит `/start` если уже авторизован)
2. **Бот** отображает сообщение:

```
🔐 АВТОРИЗАЦИЯ В СИСТЕМЕ

Выберите способ авторизации:
```

**Кнопки:**
- `📧 АВТОРИЗАЦИЯ ПО EMAIL`

---

#### Сценарий 2: Ввод email и проверка в Apex

1. **Пользователь** выбирает: `📧 АВТОРИЗАЦИЯ ПО EMAIL`
2. **Бот** запрашивает email:

```
Введите ваш корпоративный email:
```

3. **Пользователь** вводит email (например, `name@company.com`)
4. **Бот** выполняет проверку в системе Apex
5. **Результаты проверки:**

   **A. Успех:**
   - Бот отправляет 4-значный код на указанный email
   - Сообщение:

   ```
   Код отправлен на name@company.com.
   Введите 4-значный код из письма:
   ```

   **B. Пользователь не найден (первая попытка):**

   ```
   ❌ Пользователь с таким email не найден.
   Попробуйте другой email или выберите иной способ авторизации.
   ```

   **Кнопка:** `📧 ДРУГОЙ EMAIL`

   **C. Пользователь не найден (вторая попытка подряд):**

   ```
   ❌ Пользователь не найден.
   Обратитесь к руководителю проекта (РП) для получения доступа.
   ```

---

#### Сценарий 3: Ввод кода подтверждения

1. **Пользователь** вводит 4-значный код
2. **Результаты проверки:**

   **A. Успешная проверка:**

   ```
   ✅ Авторизация успешна!
   ```

   - Бот получает из Apex список проектов пользователя
   - Отображается список проектов с названиями
   - Кнопка «Подтвердить» для выбора проекта
   - После выбора проекта появляется кнопка `📋 Создать заявку`

   **B. Неверный код:**

   - **1-я ошибка:**
     ```
     ❌ Неверный код. Осталось попыток: 2
     ```

   - **2-я ошибка:**
     ```
     ❌ Неверный код. Осталось попыток: 1
     ```

   - **3-я ошибка:**
     ```
     ❌ Превышено количество попыток ввода кода.
     Начните авторизацию заново через 5 минут: /start
     ```

## 4. Модуль создания заявок

### 4.1. Инициализация создания заявки

#### Сценарий: Начало создания заявки

1. **Пользователь** нажимает кнопку `📋 Создать заявку`
2. **Бот** проверяет:
   - Актуальность авторизации пользователя в Apex (проверка почты)
   - Лимиты на создание заявок (см. раздел 7.2)
3. **Бот** отправляет инструкцию:

```
📝 СОЗДАНИЕ НОВОЙ ЗАЯВКИ

Введите подробное описание проблемы и прикрепите до 10 фотографий, если необходимо.

Требования к описанию:
• Минимум 20 символов
• Максимум 1000 символов
• Не должно состоять из повторяющихся символов

Для отмены введите /cancel
```

---

### 4.2. Ввод и валидация данных заявки

#### Сценарий: Обработка данных от пользователя

1. **Пользователь** отправляет текст описания и/или фотографии
2. **Система проверяет:**
   - **Длина текста**: 20-1000 символов
   - **Качество текста**: отсутствие повторяющихся символов ("aaaa")
   - **Количество фото**: до 10 файлов
   - **Тип файлов**: только изображения (JPEG, PNG, JPG)
   - **Размер файлов**: до 10 МБ каждый

3. **Результаты проверки:**

   **A. Успех:** переход к подтверждению заявки (см. 4.3)

   **B. Ошибка:**

   ```
   ❌ Описание проблемы должно содержать:
   • Минимум 20 символов
   • Развернутое описание
   • Не состоять из повторяющихся символов

   Введите описание повторно:
   ```

### 4.4. Финальная обработка заявки

#### Сценарий A: Подтверждение создания

1. **Бот** отправляет email на `assyst.inbox@onlanta.ru` с данными заявки:
   - **Subject:** Краткое описание (первые 100 символов)
   - **Body:**
     ```
     Проект: [Название проекта]
     Пользователь: [Имя Фамилия]
     Email: [user@company.com]
     Телефон: [+7XXX XXX XX XX]
     
     Описание проблемы:
     [Полное описание]
     
     Заявка создана через Telegram-бот.
     ```
   - **Attachments:** прикрепленные фотографии

2. **Бот** сохраняет информацию о заявке в локальной БД:
   - email пользователя
   - chat_id Telegram
   - проект
   - описание
   - дата создания
   - статус: "Отправлена"
   - временная метка для лимитов

3. **Бот** отправляет пользователю временное подтверждение:

```
⏳ Заявка отправлена в обработку...

Ожидайте подтверждения регистрации.
```

4. **После получения webhook от Assyst** (см. раздел 6.1) бот обновит статус и отправит финальное уведомление.

## 5. Модуль просмотра заявок

### 5.1. Команда `/myrequests`

**Источник данных:** только БД бота (без прямых запросов в Assyst).

#### Сценарий: Просмотр списка заявок

1. **Пользователь** вводит `/myrequests`
2. **Бот:**
   - Определяет пользователя по chat_id
   - Выбирает из БД все заявки пользователя
   - Формирует постраничный список

3. **Формат сообщения:**

```
Список ваших заявок:
```

**Кнопки (по 3 в ряд):**
```
📋 R-12345678  📋 R-1234578  📋 R-1234567
📋 R-12345679  📋 R-1234580  📋 R-1234581

        ◀️ Предыдущая      Следующая ▶️
```

4. **Пагинация:**
   - По 6 заявок на странице
   - `◀️ Предыдущая` — переход к предыдущей странице (если есть)
   - `Следующая ▶️` — переход к следующей странице (если есть)

5. **При выборе заявки:**
   - Переход к детальному просмотру (см. 5.2)

6. **Если список пуст:**

```
У вас пока нет заявок. Создайте новую через /start
```

---

### 5.2. Детальная информация о заявке

#### Сценарий: Просмотр деталей

По нажатию на кнопку конкретной заявки бот отправляет:

```
📋 Заявка R-1234567
📊 Статус: В работе
🏢 Проект: ПИКТ
📅 Создана: 19.01.2025 13:23
🎯 Описание: Текст заявки.
📎 Вложений: 1
```

**Кнопка:**
- `🗂 Назад к списку` — возврат к списку `/myrequests` с сохранением страницы

**Поля:**
- **Номер** — `eventReference` из БД
- **Статус** — текущий статус из БД
- **Проект** — название проекта
- **Дата создания** — дата и время заведения заявки
- **Описание** — текст заявки
- **Вложения** — количество файлов (если есть)

## 6. Модуль уведомлений и синхронизации с Assyst

### 6.1. Регистрация новой заявки в Assyst (type: `new`)

#### 6.1.1. Условие на стороне Assyst

Первое действие `ASSIGN` на:
- Реквесте (префикс `R`), или
- Инциденте (без префикса)

#### 6.1.2. Webhook от Assyst

**Endpoint:** `POST /itsm-bot/webhook`

**Payload:**
```json
{
  "type": "new",
  "email": "example@mail.ru",
  "incidentId": 512345,
  "eventReference": "R12345",
  "status": "В работе",
  "subject": "Не работает принтер",
  "description": "Не работает принтер\nВсе плохо"
}
```

**Параметры:**
- `type` (string) — тип события: `"new"`
- `email` (string) — почтовый ящик пользователя
- `incidentId` (int) — внутренний ID заявки в Assyst
- `eventReference` (string) — номер заявки для отображения (например, `R12345`)
- `status` (string) — текущий статус заявки
- `subject` (string) — тема заявки
- `description` (string) — описание заявки

#### 6.1.3. Обработка на стороне бота

1. **Создать/обновить запись в БД:**
   - `incidentId`
   - `eventReference`
   - `email`
   - `status`
   - `subject`
   - `description`
   - дата создания

2. **Определить пользователя:**
   - Найти chat_id по `email` в БД

3. **Отправить уведомление пользователю:**

```
✅ Ваше обращение зарегистрировано.
Присвоен номер R1186342.
```

**Кнопка:**
- `📋 Открыть заявку` — переход к деталям заявки (см. 5.2)

4. **Ответ Assyst:**
   - `201 Created` — запись успешно создана

---

### 6.2. Остановка таймера (type: `clockstop`)

#### 6.2.1. Условие на стороне Assyst

Действие `PENDING xxx` на Реквесте или Инциденте.

#### 6.2.2. Webhook от Assyst

**Endpoint:** `POST /itsm-bot/webhook`

**Payload:**
```json
{
  "type": "clockstop",
  "email": "example@mail.ru",
  "incidentId": 512345,
  "eventReference": "R12345",
  "status": "В ожидании",
  "statusdesc": "Запрошена уточняющая информация"
}
```

**Параметры:**
- `statusdesc` (string) — текст из действия `PENDING xxx`

#### 6.2.3. Обработка на стороне бота

1. **Обновить запись в БД:**
   - Найти заявку по `incidentId` или `eventReference`
   - Обновить `status` на `"В ожидании"`
   - Сохранить `statusdesc`

2. **Отправить уведомление пользователю:**

```
🔔 Статус заявки изменился!
🔢 Номер: R12345
📊 Новый статус: В ожидании
📌 Причина смены статуса: Запрошена уточняющая информация
📅 Время: 19.01.2025 13:23
```

**Кнопка:**
- `📋 Открыть заявку`

3. **Ответ Assyst:**
   - `200 OK`

---

### 6.3. Запуск таймера (type: `clockstart`)

#### 6.3.1. Условие на стороне Assyst

- Действие `START CLOCK` на Реквесте/Инциденте, или
- Действие `RE-OPEN` на Инциденте

#### 6.3.2. Webhook от Assyst

**Endpoint:** `POST /itsm-bot/webhook`

**Payload:**
```json
{
  "type": "clockstart",
  "email": "example@mail.ru",
  "incidentId": 512345,
  "eventReference": "R12345",
  "status": "В работе",
  "statusdesc": ""
}
```

#### 6.3.3. Обработка на стороне бота

1. **Обновить запись в БД:**
   - Найти заявку по `incidentId` или `eventReference`
   - Обновить `status` на `"В работе"`
   - Очистить `statusdesc` (NULL или пустая строка)

2. **Отправить уведомление пользователю:**

```
🔔 Статус заявки изменился!
🔢 Номер: R12345
📊 Новый статус: В работе
📅 Время: 19.01.2025 13:45
```

**Кнопка:**
- `📋 Открыть заявку`

**Примечание:** Строка "Причина смены статуса" не выводится.

3. **Ответ Assyst:**
   - `200 OK`

---

### 6.4. Закрытие заявки (type: `closed`)

#### 6.4.1. Условие на стороне Assyst

- Действие `PENDING-CLOSURE` на Реквесте/Инциденте **без согласования закрытия**, или
- Успешная обработка согласования закрытия на Инциденте

#### 6.4.2. Webhook от Assyst

**Endpoint:** `POST /itsm-bot/webhook`

**Payload:**
```json
{
  "type": "closed",
  "email": "example@mail.ru",
  "incidentId": 512345,
  "eventReference": "R12345",
  "status": "Решено",
  "rate": [
    {
      "vote": 5,
      "link": "https://quality-rating.onlanta.ru/v2/ratereq.php?q=58b0ae868516341dcbd2a7d4aafe7582a6a79d30&r=6194716&u=0&rate=5"
    },
    {
      "vote": 4,
      "link": "https://quality-rating.onlanta.ru/v2/ratereq.php?q=58b0ae868516341dcbd2a7d4aafe7582a6a79d30&r=6194716&u=0&rate=4"
    },
    {
      "vote": 3,
      "link": "https://quality-rating.onlanta.ru/v2/ratereq.php?q=58b0ae868516341dcbd2a7d4aafe7582a6a79d30&r=6194716&u=0&rate=3"
    },
    {
      "vote": 2,
      "link": "https://quality-rating.onlanta.ru/v2/ratereq.php?q=58b0ae868516341dcbd2a7d4aafe7582a6a79d30&r=6194716&u=0&rate=2"
    },
    {
      "vote": 1,
      "link": "https://quality-rating.onlanta.ru/v2/ratereq.php?q=58b0ae868516341dcbd2a7d4aafe7582a6a79d30&r=6194716&u=0&rate=1"
    }
  ]
}
```

**Параметры:**
- `status` (string) — `"Решено"` или `"Отклонено"`
- `rate` (array) — массив вариантов оценки:
  - `vote` (int) — значение оценки (1-5)
  - `link` (string) — ссылка для оценки

**Определение статуса:**
- `"Отклонено"` — реквест имеет этап `DECLINED`
- `"Решено"` — во всех остальных случаях

#### 6.4.3. Обработка на стороне бота

1. **Обновить запись в БД:**
   - Обновить `status` на `"Решено"` или `"Отклонено"`
   - Пометить заявку как закрытую

2. **Отправить уведомление с оценкой:**

```
✅ Заявка R12345 Решено.

Пожалуйста, оцените качество обслуживания:
```

**Кнопки (5 вариантов):**
- `⭐️⭐️⭐️⭐️⭐️` → открывает `rate[0].link`
- `⭐️⭐️⭐️⭐️` → открывает `rate[1].link`
- `⭐️⭐️⭐️` → открывает `rate[2].link`

- `⭐️` → открывает `rate[4].link`

### 6.5. Запрос согласования закрытия (type: `confirmation`)

#### 6.5.1. Условие на стороне Assyst

Действие `USER_CONFIRMATION_REQ` на Реквесте или Инциденте.

#### 6.5.2. Webhook от Assyst

**Endpoint:** `POST /itsm-bot/webhook`

**Payload:**
```json
{
  "type": "confirmation",
  "email": "example@mail.ru",
  "incidentId": 512345,
  "eventReference": "R12345",
  "status": "Согласование закрытия",
  "confirmation": {
    "description": "Текст согласования закрытия",
    "attachments": [
      {
        "filename": "text.txt",
        "data": "base64_encoded_content"
      }
    ],

  }
}
```

**Параметры:**
- `confirmation` (object) — данные согласования:
  - `description` (string) — текст согласования
  - `attachments` (array) — вложения (filename + data в base64)
  - `confirm` (string) — тема письма для согласования
  - `deny` (string) — тема письма для отклонения

#### 6.5.3. Обработка на стороне бота

1. **Обновить запись в БД:**
   - Обновить `status` на `"Согласование закрытия"`
   - Сохранить данные `confirmation`

2. **Отправить уведомление пользователю:**

```
🔔 Требуется ваше согласование!
🔢 Номер заявки: R12345
📝 Описание: Текст согласования закрытия
📎 Вложения: 1 файл
```

**Вложения:**
- Декодировать base64 и отправить файлы как документы в Telegram

**Кнопки:**
- `✅ Согласовать`
- `❌ Отклонить`

## 7. Система безопасности и ограничений

### 7.1. Безопасность авторизации

- **Срок действия кода:** 5 минут
- **Максимум попыток ввода:** 3
- **Блокировка после 3 ошибок:** 5 минут
- **Формат кода:** 4 цифры (0000-9999)

#### Проверка пользователей

- **Максимум попыток поиска email:** 2 подряд
- После 2 неудачных попыток: сообщение об обращении к РП

### 7.2. Ограничения создания заявок

#### Лимиты

1. **Максимум заявок в час:** 5
2. **Максимум заявок в сутки:** 10
3. **Интервал между заявками:** 15 минут

#### Сообщения при превышении лимитов

**Часовой лимит:**
```
❌ Превышено количество заявок в час (5/5).
Доступно создание новой заявки через: [X] минут.
```

**Суточный лимит:**
```
❌ Превышено количество заявок в сутки (10).
Новые заявки будут доступны завтра.
```

**Интервал не пройден:**
```
❌ Слишком частые запросы.
Следующую заявку можно создать через: [X] минут.
```

---

### 7.3. Безопасность данных

- Хранение паролей и токенов в зашифрованном виде
- Использование HTTPS для всех внешних запросов
- Логирование всех действий пользователей
- Регулярная очистка устаревших сессий

## 8. Валидация данных

### 8.1. Проверка email

- **Формат:** стандартный email формат (RFC 5322)
- **Обязательное поле**
- Проверка существования в системе Apex

### 8.2. Проверка описания проблемы

#### Требования

- **Минимальная длина:** 20 символов
- **Максимальная длина:** 1000 символов

#### Запрещенные паттерны

- Повторяющиеся символы ("aaaa", "1111", более 3 подряд)
- Только пунктуация или специальные символы
- Пустые или состоящие только из пробелов строки

#### Примеры валидных описаний

```
✅ Не работает принтер HP LaserJet в кабинете 305. При попытке печати выдает ошибку "Paper jam".
✅ Проблема с доступом к корпоративной почте. Не могу войти в Outlook с утра.
```

#### Примеры невалидных описаний

```
❌ ааааа
❌ 11111111111111
❌ помогите
❌ !!!!!!!!!!!!
```

---

### 8.3. Проверка файлов

#### Требования к файлам

- **Максимум файлов:** 10 на одну заявку
- **Поддерживаемые форматы:** JPEG, PNG, JPG
- **Максимальный размер файла:** 10 МБ
- **Общий размер всех файлов:** до 50 МБ

#### Обработка ошибок

**Неподдерживаемый формат:**
```
❌ Неподдерживаемый формат файла. Разрешены только JPEG, PNG, JPG.
```

**Превышен размер:**
```
❌ Размер файла превышает 10 МБ. Пожалуйста, уменьшите размер или выберите другой файл.
```

**Слишком много файлов:**
```
❌ Превышено максимальное количество файлов (10).
Удалите лишние файлы и попробуйте снова.
```

## Приложение C: Глоссарий

| Термин | Описание |
|--------|----------|
| **Assyst** | Система управления заявками (Service Desk) |
| **Apex** | Система для проверки пользователей и управления проектами |
| **БД бота** | Локальная база данных Telegram-бота |
| **Webhook** | HTTP callback для уведомления о событиях |
| **eventReference** | Номер заявки для отображения пользователю (например, R12345) |
| **incidentId** | Внутренний ID заявки в Assyst |
| **chat_id** | Уникальный идентификатор пользователя в Telegram |
| **РП** | Руководитель проекта |
| **СИБ** | Служба информационной безопасности |
| **ПД** | Персональные данные |
